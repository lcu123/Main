# CLAUDE.md — Zest FieldRoutes MCP

Context file for Claude Code / any agent working in this repo. Read fully before changing anything.

## Goal

A remote MCP server that gives Claude (claude.ai web/mobile, Cowork, Claude Desktop) read **and write** access to Zest Lawn & Pest's FieldRoutes account. Priorities, in order:

1. Answer office questions fast: which property is assigned to which route/tech, what's due for service, what a tech must know before a stop (Red Notes, flags, alerts), who owes money.
2. Take safe actions: notes, tasks, schedule/reschedule/cancel/complete appointments, hold a spot, update Red Notes, change subscription scheduling (frequency, billing frequency, seasonal window, custom date, region, preferred tech/day/time).
3. Reach every FieldRoutes endpoint without bloating context: 31 curated tools by default, all 187 endpoints via generic tools, optional per-endpoint generation.
4. Never surprise the owner: deletes and real card charges are blocked unless explicitly enabled; writes can be switched off per deployment, or restricted to a test customer while validating a new deployment.

## Non-goals

- Not a general FieldRoutes SDK. Tool outputs are trimmed to what an office user reads, not full records (use `get` for full records).
- Not multi-tenant. One FieldRoutes office per deployment; run a second Railway service for another office or a read-only variant.
- Not OAuth. Access control is a secret path segment (claude.ai's connector UI has no header field). Treat the URL as a password.
- No API field controls FieldRoutes' "Autoschedule" (Due Date Method) setting, or lets you define the dates of a Custom Schedule (only pick an existing one by ID). Both stay UI-only; don't invent params for them.

## How FieldRoutes' API actually works (do not "fix" these)

Built from the official Swagger spec (`src/fr_mcp/fieldroutes_spec.json`, extracted by `scripts/extract_spec.py` from `https://api.fieldroutes.com/resources/swagger.js`, which is itself the real spec, not a mock). Every earlier third-party MCP got this wrong:

- `POST https://{subdomain}.fieldroutes.com/api/{entity}/{action}` — `.pestroutes.com` also works (`FR_BASE_URL` override).
- Body is `application/x-www-form-urlencoded`, **not JSON**. `authenticationKey` and `authenticationToken` go in the body. **httpx 0.28 gotcha:** `AsyncClient.post(url, data=list_of_tuples)` silently degrades to a sync-only content stream and crashes an async client (`data=` is only treated as form-urlencoded when it's a `Mapping`). `client.py` pre-encodes with `urlencode()` and sends via `content=` plus an explicit `Content-Type` header instead. Don't switch this back to `data=`.
- Arrays are PHP-style repeated keys: `customerIDs[]=1&customerIDs[]=2`.
- Search filters are JSON strings: `balance={"operator":">","value":"0"}`. Operators: `> < >= <= = != IN BETWEEN LIKE STARTSWITH ENDSWITH CONTAINS`. A plain list in a search filter is sent as an `IN` object (`client.normalize_search_filters`).
- Responses are JSON; HTTP is 200 even on failure (`success: false` + `errorMessage`). **Verified live on `office/search` and `office/get`**, every response also carries an envelope the swagger doesn't document: `params` (an echo of the *entire request, authentication key and token included* — `client.call()` strips it before returning, never reintroduce it into tool output), `tokenUsage` (FieldRoutes' own `requestsReadToday`/`requestsWriteToday` — authoritative, shared across integrations, survives our restarts; `UsageCounter.sync()` adopts it over our estimate), `tokenLimits`, `requestAPIKeyType`, `requestAction`, `endpoint`, `ignoredParams` (a **list**, and it precedes the data key — so "first list in the body" can never be how records are found), `processingTime`, `count`. `search` returns the ID list under `{entity}IDs` (singular entity name; `idName`/`propertyName` both name that key) and, with `includeData=1`, the first 1000 resolved records under the **plural** entity name (`offices`, not `office`) named by `propertyNameData`, plus `{entity}IDsNoDataExported` for the rest, which come via `get` in chunks of 1000. `get` returns records under the plural name too, named by `propertyName`. `client.extract_records()` trusts those name hints first, then plural/singular, then a metadata-aware scan — don't shortcut it.
- **`get`'s bulk-ID param is *not* always `{entity}IDs`.** 24 of 56 entities deviate: `serviceType/get` takes `typeIDs`, `cancellationReason/get` takes `reasonIDs`, `customerFlag/get` takes `customerIDs` (it has no ID of its own — its "get" returns every flag row for those customers), `applicationMethod/get` takes the FieldRoutes-side-misspelled `applciationMethodIDs`, and 20 more. `extract_spec.py` derives the real one per entity (every `get` endpoint has exactly one array-typed param — that one) into `entities.{entity}.getIdParam`; `server._id_param(entity)` reads it, defaulting to `{entity}IDs` when unset. Always fetch through `_get_rows`/`_search_rows`, never hand-roll a `{entity}IDs` key.
- FieldRoutes' own swagger has real defects, not just gaps: `compassCustomer/search` has three params with `name: 0/1/2` (types `"o"`/`"c"`/`"d"`, evidently a string exploded character-by-character by their spec generator). `extract_spec.py`'s `slim_param` drops any param whose name isn't a valid Python identifier rather than crash tool registration. If a future re-extraction adds new junk like this, it'll be silently dropped the same way — check `describe_endpoint` output if an entity seems to be missing an obvious param.
- Rate limits: 60 req/min/office; 3,000 reads + 3,000 writes/day, **shared with every other integration touching the office** (FieldRoutes' own UI, Zapier, website forms). `client.py` has a sliding-window rate limiter at 55/min, and a `UsageCounter` that tracks this server's own reads/writes per local day and refuses new calls of a kind at 95% of `FR_DAILY_READ_LIMIT`/`FR_DAILY_WRITE_LIMIT` (default 3000 each) rather than running the office's shared quota to zero. This is a self-imposed estimate, not authoritative — FieldRoutes' server is.
- Field names that matter: customers use `fname`/`lname`/`phone1`; the customer's **Red Notes = `customer.notes`**, permission `editRedNotes`. **Verified live** (Zest customer 10000, 2026-09-03): despite the published spec declaring `notes` write-only and omitting it from `customer/get`'s response schema, the real API *does* return it on `customer/get` once a value has been set -- round-tripped a test string through `set_red_notes` → `customer_alerts` (which reads `customer.notes` via `_get_rows("customer", ...)`) and got it back verbatim, then cleared it back to empty. `customer_alerts`/`set_red_notes`'s existing blind-overwrite implementation is correct as shipped; no read-before-write revisit needed. Don't confuse this with an office's own custom Note Type that happens to be *named* "Red Note" (e.g. Zest's is typeID 8, Admin → Preferences → Note Types -- per-office config, not a fixed ID) -- that's a normal timestamped `note` entity row, a completely separate mechanism from the `customer.notes` banner field. Confirmed unrelated: writing `customer.notes` via `set_red_notes` created zero new rows in `list_notes`.
- **Verified live on `customer/get`**: every field value comes back as a JSON *string*, even numeric/ID ones (`"customerID": "10000"`, `"balance": "0.00"`) — `_int()`/`float()` handle this fine, no fix needed. More importantly, `customer.subscriptionIDs` and `customer.appointmentIDs` are **comma-separated strings** (`"appointmentIDs": "10002,10006,16404"`), not JSON arrays, despite the swagger's declared `type: array` — same pattern as `additionalTechs`. Passing that string straight into `_get_rows()` used to iterate it character-by-character (a real bug this caught: `"12,34"` silently became IDs 1, 2, 3, 4 instead of 12 and 34, which for a customer with a multi-digit or second subscription ID would fetch the wrong subscription). Always route a customer's own ID-list fields through `_id_list()`, never index them directly. Also: the live record carries several fields the swagger doesn't declare at all (`customerNumber`, `lotSize`, `subPropertyType`, `customerSubSourceID`/`customerSubSource`, `districtCode1`-`5`) — the spec's field list is a floor, not a ceiling; don't assume it's exhaustive when reading a live record.
- Scheduling notes = `specialScheduling` (on `customer`, read-only from the tools' perspective — no curated write for it yet). Alerts = `task` with `type=1` (`type=0` is a plain task); task `category`: Billing 1, Customer Care 10, Appt Status 15. Notes need `contactType` (Note Type ID from Admin → Preferences → Note Types; no API endpoint lists them) — note's own row ID in write params is **`contactID`, not `noteID`** (`note/update`, `note/delete`). Cancel uses `cancelReason` (string) + `cancelledBy` (employeeID). Appointment `status`: 0 pending / 1 completed / 2 no-show. Subscription `active`: 1 active / 0 frozen / -3 lead. Routes/spots expose `apiCanSchedule`. `appointment.additionalTechs`/`route.additionalTechs` are **comma-separated strings** of employeeIDs, not arrays (confirmed against the spec's own type declaration) — `_emp_list()` splits on `,`. `customer/get` takes `includeCustomerFlag=1` to inline the customer's flags (array under `customerFlag`); flags are also independently reachable via the `customerFlag` entity (`customerIDs`/`customerFlags` filters).

## Conventions

- Every tool returns a JSON string via `_j()`. Trim records with `_pick(row, KEYS)`; the `*_KEYS` lists at the top of `server.py` define what an office user sees. Add a key there rather than dumping whole records.
- Curated reads should resolve IDs to names (`_emp_names`, customer lookups) and put the **property address** on any row that has a customer. When you already have the customer record in hand (e.g. `customer_360` fetching its own appointments/subscriptions), pass it into `_shape_appointments`/`_shape_subscriptions`' `customers` map instead of letting them re-fetch — a redundant `customer/get` costs a real call against the shared daily quota.
- Dates: `YYYY-MM-DD`; datetimes `YYYY-MM-DD HH:MM:SS`, office local time (`TZ` env var — Railway defaults to UTC). Default windows are today + 6 days.
- `FR_OFFICE_ID` is auto-applied to searches when set and no office filter is given.
- Writes go through `_writes_enabled()`, then `_require_customer_allowed()` (the `FR_WRITE_CUSTOMER_IDS` allowlist — see below). Anything that could cancel, charge, freeze, or overwrite Red Notes must confirm with the user (say so in the docstring — Claude reads it).
- **Write allowlist** (`FR_WRITE_CUSTOMER_IDS`, comma-separated customer IDs): when set, a write is refused unless it resolves to one of those customers. Direct-customer-ID tools (`add_note`, `set_red_notes`, `create_task`, `schedule_appointment`) check immediately; record-based tools (`update_note`, `reschedule_appointment`, `update_appointment_notes`, `cancel_appointment`, `complete_appointment`, `update_subscription`) fetch the existing record first via `_write_target_customer(entity, id)` — which is a no-op returning `None` instantly when the allowlist isn't set, so this costs nothing once the deployment goes live and the variable is cleared. `reserve_slot` is the one deliberate exemption: a spot hold names no customer and isn't customer data. The generic `call` tool and every generated tool go through the same `_resolve_write_customer()`/`_require_customer_allowed()` pair — fail closed: an entity with no customer relationship at all (route, spot writes other than reserve, employee, service type, ...) resolves to `None` and is refused when the allowlist is active, not silently allowed through.
- Generic `call` and generated tools share guards: `*/delete` needs `FR_ALLOW_DELETE=1`; `payment/create` with `doCharge=1` needs `FR_ALLOW_CHARGES=1`.
- Errors: raise `FieldRoutesError`; the `_tool` wrapper (curated tools) / inline `try/except` (generic `call`, generated tools) converts it to `ToolError` so the message reaches Claude.
- Tool docstrings are the schema descriptions. One or two sentences; say when to use it and what it returns. Context cost matters: 31 curated tools measure ~24.7k chars of schema JSON (~6.2k tokens at a rough 4-chars/token estimate; `test_context_budget.py` pins this with headroom) -- higher than a naive per-tool estimate because pydantic wraps every optional `X | None = None` param in an `anyOf`/`title` structure. `FR_EXPOSE_ALL` (187 endpoints) is roughly 10x that.
- mcp SDK is **2.x** (`mcp.server.mcpserver.MCPServer`, not `FastMCP`; `ToolError` is `mcp.server.mcpserver.exceptions.ToolError`). Transport is streamable-HTTP, stateless, JSON responses, DNS-rebinding protection off (Railway hostnames). `mcp.call_tool()` returns a `CallToolResult` with `.content[0].text`, not a subscriptable list — if you're writing a test against it directly, don't index it.
- Generated tools are built with a dynamically-constructed `inspect.Signature` (real `inspect.Parameter` objects with proper annotations) attached to a `**kwargs`-accepting async function, not a hand-written one per endpoint. This is required for the MCP SDK's Pydantic-based schema derivation (`Tool.from_function`) to produce an accurate per-tool JSON schema, `required` fields included, from spec data at startup.
- Never log the HTTP request path in the `http` transport — it contains `MCP_PATH_SECRET`. `main()` runs uvicorn with `access_log=False` and never prints the resolved secret path (`/<secret>/mcp` in the startup log, not the real value). Don't reintroduce either.

## Adding a tool

1. Check `describe_endpoint`/the spec for exact param names. Do not invent names — and don't assume `{entity}IDs` for a bulk-get id param; check `entities.{entity}.getIdParam` or just call `describe_endpoint`.
2. Write it next to similar tools in `server.py`, decorated `@_tool` (not `@mcp.tool()` directly — `_tool` wraps `FieldRoutesError` into `ToolError`), returning `_j(...)`.
3. Resolve IDs to names, include the property address, trim with `_pick`.
4. If it writes: call `_require_writes(tool)`, then `_require_customer_allowed(tool, customer_id)` — either directly (if the tool already takes `customer_id`) or via `await _write_target_customer(entity, record_id)` if it only takes an existing record's ID. If it can cancel/charge/delete/freeze/overwrite Red Notes, say "confirm with the user" in the docstring.
5. Add the tool to the README table, this file's inventory (and count), and `test_http_app_secret_path_healthz_and_bearer`'s expected tool count. Run `pytest`.

## Verified against the live Zest tenant (2026-09-03)

The README's first-run checklist has been run against Zest's real account (`zestlawnpest.fieldroutes.com`, office 1), `FR_WRITE_CUSTOMER_IDS=[10000]` (customer "Test Sean") throughout. Results:

- `health_check`, `lookups`, `find_customer`/`customer_360`, `day_schedule`, `crew_schedule` all correct against real data on the first try.
- **Red Notes resolved** -- see the field-names note above. `customer_alerts`/`set_red_notes` needed no changes.
- **`subscription/update` does a true partial update** -- confirmed by changing one field (`duration` 15→16) on a real subscription and reading every other field back byte-identical, then reverting. This was the one open question that could have silently corrupted a subscription; it's safe.
- **Found and fixed live**: `add_note`'s `note_type = note_type_id or _default_note_type()` dropped an explicitly-passed `note_type_id=0` (Python falsy-zero) -- and Zest's account has a real Note Type with ID 0 ("Notes", Admin → Preferences → Note Types). Fixed to an explicit `is not None` check. Checked every other `x or _default_y()` pattern in `server.py`: `employee_id or _default_employee()` (two call sites) is fine as-is, since `0` is FieldRoutes' own "unassigned" sentinel for employee fields everywhere else in the live API (confirmed against real `assignedTech`/`preferredTechID` values) -- never a real employee ID at this office (real ones start at 10000).
- **Real blocker, not a code bug**: every `spot` office-wide (past, present, and future) has `apiCanSchedule: "0"` -- confirmed via a direct `spot/search` with no date/route restriction. This is exactly the risk this file already flagged ("API key lacking 'can schedule' permission"). `schedule_appointment`/`open_slots`/`reserve_slot` can't be meaningfully tested until this is granted in FieldRoutes Admin → API → Manage Keys (or whatever office-wide setting controls it) -- ask the owner before assuming it's the API key specifically.
- **Fixed**: `due_for_service`'s default `limit=200` produced a 200K+ character response against Zest's real subscription volume -- too large for a single tool response in practice. Default lowered to 50 (still fully overridable -- pass a higher `limit` once narrowed by service type/region/tech for a bigger pull), and its output now uses `DUE_FOR_SERVICE_KEYS`, a trimmed subset of `SUBSCRIPTION_KEYS` dropping billing/sales/administrative fields (`soldBy*`, `billingFrequency`, `contractValue`, `agreementLength`, etc.) that a "what's due" skim doesn't need. `subscription_details`/`service_schedule` are untouched -- they still pass the full `SUBSCRIPTION_KEYS` to `_shape_subscriptions` via its new optional `keys` param.
- Confirmed live: `subscriptionID: "-1"` (the stand-alone sentinel) appears in real appointment data (e.g. appointment 16707), corroborating the `service_schedule` fix that excludes it from `subscription/get` lookups.
- **Second pass against real customers (14699, 14964, 19741 -- read-only) found a whole bug class the fake couldn't see, all fixed**: every live field value is a *string*, so `"0"` is truthy -- `route_stops` labeled every open spot "reserved", `_shape_subscriptions` rendered `region: "0"` for unassigned regions and emitted `soldBy2Name: null` noise. Rule: **never truth-test a raw FieldRoutes field; go through `_int()`** (`open_slots` already did; `route_stops` didn't). Same pass: `frequency` arrives as the literal string `"CUSTOM"` for custom-schedule subscriptions (not `-3`); `customer/search`'s `phone` param is an exact 10-digit match across phone1/phone2/additional contacts and **neither `phone` nor `phone1` honors CONTAINS** (returns zero rows silently -- `find_customer(phone=...)` was returning nothing on live until fixed to send a bare normalized number; partial numbers can't be searched at all); an appointment's `employeeID` is who *booked* it (office staff, or `FR-System-Job` for imports), not the tech -- `_shape_appointments` now falls back to the route's tech instead and reports `bookedBy` separately; live names/addresses carry stray whitespace (`"Pedro "`, a leading tab), normalized via `_clean()`. `tests/conftest.py`'s seed now carries a string-valued spot (35) and subscription (101) so the fake models these shapes.
- **Write pass (customer 10000 only), every call read back afterwards**: `add_note`, `update_note`, `set_red_notes`, `update_subscription`, `reschedule_appointment` (duration/time-window only -- no spot needed), `update_appointment_notes`, `create_task`, and generic `call` writes (`appointment/update`, `task/update`) all verified live. Three things only a real write could show, all fixed: (1) `appointment/update` has **no office-notes param** -- the tool sent `officeNotes`, FieldRoutes answered `success: true` with `ignoredParams: ["officeNotes"]` and wrote nothing; `office_notes` is gone from `update_appointment_notes` (`appointment/complete` does accept `officeNotes`, so `complete_appointment` keeps it). (2) That silent-drop pattern is now an error everywhere: `client.call()` raises `FieldRoutesError` when a param we sent shows up in `ignoredParams` -- for a write that means a partial save, for a search an ignored filter means *unfiltered* rows. `FakeFR.ignore_params` models it. (3) `task/create` **requires** `category`, rejects `0` and the spec's built-in IDs (`10` → "not a valid taskCategoryID for the office"), and only accepts the office's own Task Categories, which have no listing endpoint -- Zest's only one is `10002 "Billing"`; every human-made task otherwise carries `category "0"`. `create_task` now falls back to `FR_DEFAULT_TASK_CATEGORY_ID` and errors clearly, and `lookups(kind="task_categories")` derives the in-use IDs from existing tasks. Also confirmed: the `notes` param of `appointment/update` lands in the record's `appointmentNotes`, and an empty string clears it.
- **`cancel_appointment` verified live** (appointment 10002, customer 10000, General Service, 2026-07-21): cancelled, read back with `status: "-1"`/`statusText: "Cancelled"`, `dateCancelled` stamped, `cancelledBy` matching `FR_DEFAULT_EMPLOYEE_ID`. Confirmed `APPOINTMENT_STATUS`'s existing `{-1: "cancelled"}` entry resolves correctly (`-1` is truthy in Python, so `_int(status) or 0` evaluates to `-1`, not `0` -- no falsy-sentinel bug here, unlike the `note_type_id=0` one above).
- **Found and fixed live, from that same cancel test**: `customer_360` (and `customer_alerts`, same pattern) sends `customer/get` best-effort `include*` params the swagger declares (`includeSubscriptions`, `includeCustomerFlag`, `includeAdditionalContacts`) that Zest's live account silently ignores -- and the new `ignoredParams`-is-an-error guard above (correctly) turned that into a hard failure, even though both tools already have working fallbacks for exactly this case (a separate `subscription/get`, `flags` defaulting to `[]`). ## Zest Visit Video (second service in this repo)

Built from the Visit Video build brief (Nov 12, 2026). A tech records one 15-second video per property visit; the customer gets an email with a link. The brief was updated on Nov 13: the rule is one video **per tech**, per property, per day. Start with `docs/video/README.md`; `docs/video/API.md` is the app-to-server contract and `docs/video/GO-LIVE.md` is what is left for the owner.

- **Two services, one image.** `fr-mcp` (this file's main subject) and `zest-video` (`src/zest_video/app.py:main`). On Railway they are separate services built from the same Dockerfile; `zest-video` sets its start command to `zest-video`. Do not import `fr_mcp.server` from `zest_video` (it builds the MCP and its tools at import); import `fr_mcp.client` only. `zest_video/fr.py` is the one place the video server talks to FieldRoutes.
- **Never surprise the owner applies here too.** Customer email is off unless `VIDEO_EMAIL_MODE` is `test` or `live`. FieldRoutes writes obey the same `FR_WRITES` / `FR_WRITE_CUSTOMER_IDS` as the MCP server and go through an outbox (`fr_outbox`) that retries, so a FieldRoutes outage never loses a note, score or task. The deployed service currently runs with `VIDEO_EMAIL_MODE=off` and `FR_WRITES=off`; do not flip either without the owner saying so.
- **Every phone-facing call is safe to repeat.** The video ID is made on the phone. A second register, complete or delete with the same ID must never create a second video or a second email. Keep it that way when touching `videos.py`.
- **The phone gets no contact data.** `/v1/today` carries name, service address, map pin and appointment IDs only (`test_the_phone_never_receives_contact_or_billing_data` pins the exact key set). The server does not store customer emails; it reads the address from FieldRoutes at the moment it sends.
- **Do not raise `ApiError` inside `engine.begin()` after a write you need kept.** The exception rolls the transaction back. This silently disabled the 5-wrong-tries lock on login codes until a test caught it; see `auth._check_code` for the pattern (decide inside, raise outside).
- **Monotonic time starts at boot.** "Never happened" must be `None` or `-inf`, not `0`. `last_tech_sync = 0.0` meant nobody could log in for the first five minutes on a fresh machine; only CI's fresh runners showed it.
- **Stops**: one row per customer per day, every appointment folded in. One video per tech per property per day: `route.tech_view(stop, tech_id)` is a tech's own share of a stop (his appointments, services, check-in, done), and everything that asks "does this stop have a video" must ask it per tech (`register`, `_deliver`, `move`, `flag_missing`, the office board and stats all do; `tests/test_video_two_techs.py` pins it). A helper listed only in `additionalTechs` shares the whole stop and his video covers it for the lead. Truth about "finished" lives in each folded appointment (`status`, `doneSeenAt`), not only in the stop's `done` column, and a tech's stop is finished once **any** of his appointments there is completed: a real week (Nov 9-13) showed about one stop in ten with the main job completed and an unassigned add-on (leaf pick-up) left pending for days, which under "all completed" never counted as finished and so was never flagged. The same week had no `additionalTechs` on any route or appointment, and one property with two techs' appointments on the same day. Tech = the appointment's `assignedTech`, falling back to the route's tech; checked against a real day where it matched `servicedBy` on all 44 completed appointments. Check-in is a hint, not proof (several real stops had check-in and check-out seconds apart), so the server's time check only ever raises a flag.
- **A start never falls back quietly.** `build_ctx` calls `config.check_start`: on a real deployment (Railway's own variables are there, or `VIDEO_BASE_URL` is a public https address) no Postgres or no bucket raises `StartRefused`; a laptop, a test and CI start with a warning. Never add a silent fallback to a file or to memory. A start goes through three gates (`app.py`'s header: settings, the database answers, the bucket and the database belong together). A refusal may only follow an answer that cannot be a passing fault: a bucket that is unreachable, slow or erroring never stops a start. "A new database beside a bucket that holds videos" means no video row **and no row in `devices`**: nobody can sign in on a database before a server has started on it, so a database with sign-ins is the one in use (old test files beside it, or videos from after a backup that was put back) and only gets a warning. Refusing it would take a working service down at its next restart.
- **The wait for the database belongs in `main()`** (`database_first`), never in the web server's own start-up: a web server that is starting ignores the stop signal until it has started. In a container the process is number 1, which is only sent a signal it asked to hear, so `main` installs its own SIGTERM handler for as long as the wait lasts.
- **`/healthz` asks only the database.** Never the bucket, FieldRoutes or the mail service: each has a fallback that loses nothing, and a bad minute at one of them must not make a working server look dead. Railway only calls it during a deploy.
- **"Not there" is only believed in the bucket's own words** (`storage.ask`: a 404 that names `NoSuchKey`). A bare 404 is somebody else's page. So is a 200 with a page of words on it (`storage.words_not_a_file`), and a 200 with no ETag. A video is pulled only on the bucket's "no such key" or on a file with another ETag than the confirmed one (`videos.file_check`; ETags are compared through `storage.plain_etag`, so a weak `W/"..."` is the same file). On anything unclear the player is let through and an email waits. Never go back to "size or ETag differs means changed". Leave `storage.head`'s answer to a 404 and the test that pins it alone; `complete` may still refuse on a plain 404, because the phone just sends again.
- **A refusal is printed once**, in plain words, with no stack and no secret: raised `from None`, secrets cut with `config.hush` before the line is shortened, and `PlainRefusal` keeps the web server from printing it a second time. Messages name variables, never values.
- **`FR_WRITES` is read by the connector's rule** in both services (`config.ON_WORDS`: on only for `on`, `1`, `true`, `yes`). Never go back to `!= "off"`. A word the server does not know is read as off and says so (`config.switch_notes`).
- **Every override is named at every start** (`config.OVERRIDES`, `override_notes`), needed or not. Never add an override without a line there.
- **There are no migrations.** `db.create_all` makes missing tables and never alters one, so a new column would not exist on the live Postgres. Everything since launch was built without one; build a migration step before adding a column.
- **A video the office must decide on is held, never emailed by itself**: state `no_email` with `email_skip` in `route.HELD_BACK` (`off_route`: the visit left the day or the tech has no work there; `second_video`: the stop changed hands and both techs filmed it; `overdue`: its email was hours late). `route.held_back()` is the one question, asked by the phone (`withOffice`), the office's Send it anyway / Pull buttons, and the words a tech is told. Nothing is written to FieldRoutes while it is held. `review_route` lets a route hold go when the route says so, never an `overdue` one, never one whose flag a person cleared, and never one whose email is hours late by then (`_hold_as_late` turns it into an `overdue` hold: this is what keeps a restore from sending a video a second time). An `overdue` hold's flag also says what the route says (`_late_what`: `overdue`, `overdue:gone`, `overdue:second:...`), in the same keyed way as the route flags.
- **"Send it anyway" answers the flag that was on the screen, nothing more.** `send_anyway` writes down what it answered (`held`, `route_told`). Pressed on a late video whose flag said nothing about the route, it is not the office placing the video against the route (`placed_by_office` leaves it out), so `_deliver` still checks the route before that email goes. Never make every `video_send_anyway` entry count as placed again.
- **A route flag is keyed on what is wrong** (`off_route:{video}:{what}`), one open per video. When that is over the flag is closed and its key changed (`:was:`), so the next thing gets a flag of its own. A flag a person cleared stays cleared for the thing they saw, not for the video.
- **`route.covers()` is the one rule for "this video stands in for yours"**: the phone list, the flags, the office page, the stats and `videos.standing` all ask it. Do not answer that question anywhere else.
- **Follow-ups are saved with their record.** A state change, its audit entry, its flag and its outbox rows go in one `engine.begin()` (`_finish`, `_end(event=, flag=, clear=)`, `_insert_video`, `complete`, `save_score`, `move`, `send_anyway`), through `add_event`, `add_flag`, `close_flags`, `_queue_fr` and `db.insert_once`. Do not catch `IntegrityError` inside a save: on Postgres it spoils the whole save (`insert_once` is ON CONFLICT DO NOTHING). A step that cannot be in the save (it reads the bucket, or looks at other videos) must be safe to repeat and must be repeated: on the phone's own retry (`_registered`, the format check in `complete`) or by the five-minute round. `test_a_server_killed_at_any_save_in_a_videos_life_loses_nothing_and_doubles_nothing` kills the server before and after every save; add a new follow-up to its list. It lives that life twice: with our own email, and with "one email" on, where the line for FieldRoutes' email is one more follow-up.
- **An outbox row is claimed before it is written.** Railway starts the new server before it stops the old, so two job loops run side by side at every deploy. Anything both could do in the same minute is claimed first with an update only one can win (`send_due`, `run_outbox`, `jobs._nudge`); inserts both could make use `db.insert_once`. A row found still marked `writing` with its claim run out was cut off mid-write: it is never tried again (FieldRoutes may have it), the office is flagged instead. A claim or lease is stamped with `db.now()` at the moment it is taken and judged from the row in the database, never with the time the pass began or from the copy read at the top of the pass: a pass slowed by FieldRoutes timing out can be older than a claim is long.
- **An email more than `overdue_hours` late waits for the office** (`videos._overdue`; owner setting, 6, 0 is off). The wait is counted by `_due_since`, not from `email_due_at`, which moves on with every try: from the end of the tech's ten minutes, or from the last time a person put the video back in line (Send it anyway, a move). The route letting a video go (`video_released`) does not start the count again. It applies only while an email or a FieldRoutes write could go; with both off the video is closed as `email_off`. Its flag never says "nobody was emailed": after a restore the server cannot know, so it says it has no record of an email and where the office can look (`_overdue_words`).
- **The mail service's "I already have one under this key" is not proof of delivery** (`notify.AlreadyTaken`, a `DeliveryError`). `_deliver` reads it as sent only when no `email_failed` entry exists for the video (a kill leaves none); otherwise it stops trying, records `send_failed` and flags the office. The key ends in a hash of the inbox, so an email to the test inbox never stands for the customer's.
- **"One email" (`fr_email_minutes` on the Settings page: 0, 30 or 60; it ships at 0)** puts the video link inside FieldRoutes' own after-service email, and ours is not sent (the owner's decision of Nov 14, 2026). The office sets FieldRoutes' email to go 30 or 60 minutes after a visit is completed and puts `{{techComments}}` in its body; the server adds one line with the link to the technician's comments on the tech's own completed appointment. It is in force for a video only when the setting is 30 or 60, `FR_WRITES` is on and the customer passes `FR_WRITE_CUSTOMER_IDS` (`videos.fr_email_for`); in every other case the video goes exactly as before. With the setting at 0 the server must do exactly what it did before it existed, and `appointment/complete` is never called: `test_switched_off_nothing_changes_and_fieldroutes_is_never_asked_to_complete_anything` pins it. Start with the section "one email" in `videos.py` and `tests/test_video_fr_email.py`.
- **`appointment/complete` is the one call here that can make a real invoice.** Its `status` defaults to Completed and it runs FieldRoutes' invoicing logic (this office syncs to QuickBooks), so on a pending appointment it completes it. FieldRoutes documents that on an already-completed one it only updates what is sent ("Idempotent Re-completion"). **That has never been run live.** Only `fr.add_to_tech_comments` may call it, and only as it does now: read the appointment fresh; refuse for good (`WriteRefused`) unless it is that customer's, its status is exactly `"1"` (`fr.completed`: through `to_int` and as the bare string, because `to_int` turns 1.9 and `true` into 1) and the read carries `notes` as a string (a read without the field is not "he wrote nothing"; the write would wipe his words); send exactly `appointmentID` and `completionNotes`, never `status` or anything else; keep the technician's own words (`fr.own_words`, not `clean`, which would run his lines together); write nothing when the link is already there. `tests/video_helpers.VideoFR` models the call, including that it completes a pending appointment, so a test can prove the server never does.
- **Nothing may come between that read and that write, and the write is sent once.** The shared client sleeps up to a minute for room under the per-minute limit and sends a request again after a timeout or a 5xx, with nobody looking in between; a visit set back to pending in that time would be completed and invoiced by the second send. So `add_to_tech_comments` asks `RateLimiter.free_slots()` before the read (room for all three calls or it does not start) and again right before the send, calls with `attempts=1`, and raises instead of retrying: the outbox comes back and that try reads first again. Do not put an `await` that can wait between the read and the send (`go`, the caller's last check, is one look at one row). What is left is one network round trip, which nothing outside FieldRoutes can close; say so, never claim more.
- **"Success" is not the line being in.** After the write the appointment is read again and compared with the read before it (`fr.LineWrite`). Link not there: tried once more, then left (`not_taken`). A field in `fr.WATCHED` reads differently (status, `dateCompleted`, who serviced or completed it, the times, `ticketID`), or his words did not come back as they went: the office gets the flag `fr_changed` at once, with what was seen. Other changed fields go on the audit entry only. FieldRoutes' own messages in its answer are kept there too.
- **Two new `email_skip` values, and only one is a hold.** `fr_email`: the link went (or is going) into FieldRoutes' email. It is not in `route.HELD_BACK`, so `went_out()` is true and the tech's stop locks. `fr_missed`: it did not make that email, or nobody can tell. It is in `HELD_BACK`, so `held_back()`, `withOffice`, Send it anyway / Pull and the tech's words follow by themselves; its flag is keyed like the other holds' (`videos.missed_key`) and saved with the hold. `review_route` leaves it to the office. A missed video never emails by itself, and Send it anyway means our own email (`fr_email_for` is 0 once the newest `PLACED_BY_OFFICE` entry is a `video_send_anyway`); that press is no word on the route either (`_answers_only_lateness`).
- **The server never says "the link is not in FieldRoutes' email" without having looked.** Like the overdue flag: after a backup was put back, a write that was cut off, or an answer that got lost, the link may be there although this server has no record of adding it, and a flag that guessed would have the office send a second email. Before a video is held as too late, at release (`_into_fr_email`) and in the outbox, the visit is read (`fr.line_on`, one read, no write). Found: it is settled as in (`found_at`). Not found: the flag says the server looked (`_missed_words(looked=)`). Could not read: it says the server cannot tell, and to look in FieldRoutes before sending; the row stays open (`unsure`) and `_settle_unsure` reads again every five minutes for up to six hours, then rewrites the flag or, when the link is there after all, puts the video back as in and closes it. `line_on` raises rather than answer "not there" when a read comes without the comments.
- **A line's row is looked at three ways** (`videos._write_comment`; the payload carries `deadline`: `dateCompleted` + the minutes − `core.FR_EMAIL_MARGIN_MINUTES`, 5, the one margin; the Settings page asks for twice that between the tech's hold and FieldRoutes' wait, and refuses the setting while `overdue_hours` is 0: `core.fr_email_problem`). Writing: before the deadline, judged with `db.now()`; FieldRoutes not answering is retried after 1, 2, 2, 3 and then every 5 minutes (`COMMENT_RETRY`, not the notes' backoff, which gave a 14-minute window two tries), the last try a minute before the deadline and never on it. Too late: nothing is written to that appointment; it is read, and then the tech's next completed appointment whose email has not gone gets the line (`_pick_again`, only after the read showed the first has no link, so one video's line is never on two), or the row is closed and the video turned into the hold in one save (`_miss`). The last look: two minutes before the deadline the visit is read once more, because the comments can be saved again without the line (the tech fixes his note, an offline phone hands in its copy); gone is added again, gone too late is a hold with a flag. The same hold when the setting was switched off or writes were: a video must never read "going into FieldRoutes' email" with nothing going. A video pulled or moved before its line was written gets no line, a customer who pressed stop meanwhile gets none, and a video pulled and put back on the same customer gets no second one (`_line_went_before`).
- **A `comment` row found cut off mid-write may be tried again; a note may not.** Only because that write reads first and adds nothing when the link is there. Do not extend it to another kind. Comment rows go first in a pass.
- **`completedAt` in a stop's folded appointments is FieldRoutes' `dateCompleted`** (a key in that JSON, not a column). A video whose tech has completed nothing at the stop yet is "not due": it stays `held` so the tech can still redo it, and the overdue rule is the only limit on the wait (do not add a second; the Settings page refuses 0 for it while this is on). While the saved list says so and is younger than `videos.wait_read` (half of FieldRoutes' delay), `_deliver` stops before any read of FieldRoutes, the bucket or the customer (`_still_waiting`), and `send_due` leaves it out of its batch customer read. So a wait costs nothing in work hours (the day is read anyway) and 2 or 4 reads of the day's list an hour otherwise, not 12. A completion time ahead of the server's clock is not believed (a wrong time zone would make every line look in time).
- **What the office page says about such a video comes from its outbox row** (`videos.comment_rows`, `line_stage`): "Going into FieldRoutes' email" while it waits, "Link added for FieldRoutes' email" with the time once FieldRoutes took it and the read back showed it, "In FieldRoutes' email" only after the last look, and only then does it count as sent in the stats. A row counts as in only by the marks this code sets (`_line_in`: `written_at`, `found_at`), never by `done_at` alone: a server from before this build marks a kind it does not know as done and writes nothing, and `_put_back_lost_lines` puts such a row back in line. The banner for customer emails being off must not call such a video unsent.
- **`withOffice`** is in `GET /v1/today` on a video only while it is held, and absent otherwise (never `false`). The app shows SENT TO OFFICE. `docs/video/API.md` has it; `test_the_phone_never_receives_contact_or_billing_data` pins every key the phone is sent.
- **Tests** run on SQLite by default and on Postgres when `VIDEO_TEST_DATABASE_URL` is set (CI does both). `make_env` never takes the machine's own deployment settings (platform empty, every override off), so a `RAILWAY_*` variable in the environment cannot fail the suite. `tests/video_helpers.py` seeds a day shaped like the live data: string-valued fields, a customer with three appointments in one visit, a business with no person, a customer with no email, a tech who exists only on the route.
- **iOS**: no third-party dependencies, no bundled fonts, Swift 5 language mode, generated project (XcodeGen, `ios/project.yml`). Anything testable lives in `ios/ZestCore` (Foundation only, tested on Linux); the app target is compiled only on the macOS CI runner, so push and read the `iOS` workflow to check a change. Every size and colour lives in `ios/ZestVideo/UI/Theme.swift`. The customer watch page, emails and office page stay Zest-branded. The `Screenshots` CI job photographs all 19 screens from the real app (`-ZestScreen <name>`, simulator builds only); look at those pictures after any UI change, since that is how every layout flaw so far was found. Current set: `docs/video/screens/`. The `ui-tests` and `sizes` jobs run 99 XCUITest cases (`ios/ZestVideoUITests`) against `ios/Scripts/fake_server.py`, including kills mid-recording and mid-upload; read the step "What failed, and what the server saw" when one fails.
